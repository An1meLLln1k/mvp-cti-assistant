## Пайплайн проекта

### 1. Сбор данных

Система использует данные из официальных и практических источников:

- **NVD** - база CVE с описаниями, CWE, CVSS и ссылками;
- **CISA KEV** - перечень уязвимостей, которые уже подтверждённо эксплуатируются;
- **CWE XML** - иерархия типов уязвимостей.

На этом этапе формируется надёжная база знаний для ассистента, основанная не на абстрактных описаниях, а на реальных и структурированных данных.

### 2. Нормализация корпуса

Сырые выгрузки из разных источников приводятся к единому формату `JSONL`.

Основные артефакты:

- `dataset_v2.jsonl` - объединённый корпус CVE из NVD и KEV;
- `dataset_v2_enriched.jsonl` - тот же корпус, дополнительно обогащённый информацией об иерархии CWE.

Это позволяет работать со всеми записями в единой структуре и упрощает автоматическую обработку данных.

### 3. Обогащение CWE-иерархией

Для каждой записи CVE, где указан CWE, в датасет добавляются дополнительные поля:

- `cwe_primary_id`
- `cwe_parent_id`
- `cwe_top_id`
- `cwe_depth`
- `cwe_path`
- `cwe_is_leaf`

Благодаря этому система учитывает не только конкретный CWE, но и его положение в иерархии. Такой подход нужен для логики **coarse-to-fine**: сначала определяется общий класс уязвимости, затем более точный уровень.

### 4. Retrieval

После получения пользовательского запроса система ищет релевантные записи в локальном корпусе.

Поиск выполняется по:

- `CVE-ID`;
- ключевым словам;
- смысловым якорям, например: `chromium`, `wordpress`, `oracle`, `sql injection`, `use-after-free`.

Задача этого этапа - найти корректный контекст до генерации ответа. Это снижает риск галлюцинаций модели и делает ответы привязанными к данным.

### 5. Формирование контекста и prompt

Найденные записи преобразуются в структурированный контекст, который включает:

- идентификатор `CVE`;
- описание;
- наличие в `KEV`;
- связанные `CWE`;
- ссылки на источники.

На основе этого контекста формируется prompt для языковой модели. В результате модель отвечает не по абстрактной памяти, а на основе конкретных найденных документов.

### 6. Generation layer

В системе предусмотрено два режима генерации:

- **mock** - заглушка для проверки архитектуры и пайплайна;
- **ollama** - локальная языковая модель (`qwen2.5:1.5b`), используемая для генерации ответа.

Итог приводится к стабильному `JSON`-формату со следующими полями:

- `summary`
- `actions`
- `kev`
- `cwe`
- `references`
- `grounded`
- `notes`

Это позволяет получать не просто текстовый ответ, а структурированный результат, пригодный для анализа, логирования и дальнейшей оценки.

### 7. Логирование и оценка

Каждый запуск сохраняется в директории `runs/`.

Для retrieval-части рассчитываются основные метрики качества:

- `Recall@K`
- `MRR`
- `No-hit accuracy`

Также можно сравнивать разные режимы ответа:

- `fallback retrieval answer`
- `mock RAG answer`
- `local LLM RAG answer`

Таким образом, проект не только генерирует ответы, но и позволяет объективно оценивать качество поиска и итогового результата.
