## Корпус данных проекта

В проекте используются несколько уровней данных:
### 08.03.2026
### 1. `cwe_hierarchy.json`
Локально построенная иерархия CWE на основе локальной копии официального CWE XML (`cwec_v4.19.1.xml`).
Файл содержит служебное отображение CWE -> parent/top/depth/path/is_leaf и используется для coarse-to-fine постановки задач по CWE.

### 2. `dataset_v1.jsonl`
Небольшой sample / prototype dataset.
Использовался на раннем этапе для быстрой проверки пайплайна retrieval, логирования и evaluation.

### 3. `dataset_v2.jsonl`
Нормализованный корпус CVE, собранный из официальных NVD JSON 2.0 year feeds (2024, 2025, 2026) и дополнительно обогащённый данными CISA KEV.
Каждая строка JSONL соответствует одной CVE-записи.

### 4. `dataset_v2_enriched.jsonl`
Расширенная версия `dataset_v2.jsonl`, дополнительно обогащённая иерархическими полями CWE:
- `cwe_primary_id`
- `cwe_parent_id`
- `cwe_top_id`
- `cwe_depth`
- `cwe_path`
- `cwe_is_leaf`

Этот файл является основной рабочей версией корпуса для retrieval и последующего RAG-прототипа.

### 15.03.2026

После реализации `RAG v0` в mock-режиме выполнен переход к **реальному локальному LLM-backend**.

#### Что сделано
- проверен вариант подключения внешнего LLM API;
- по итогам теста внешний API не был выбран как основной backend из-за ограничений доступа и зависимости от платного сервиса;
- в качестве основного направления выбран **локальный inference-подход**;
- установлен и настроен **Ollama** как локальный LLM backend;
- загружена и протестирована локальная модель **`qwen2.5:1.5b`**;
- реализован новый режим запуска:
  - `--use-llm --llm-mode ollama`;
- реализован вызов локальной модели через **локальный API Ollama**;
- retrieval-контекст теперь передаётся не только в mock-адаптер, но и в реальную локальную модель;
- собран полный локальный RAG-контур:
  - retrieval;
  - context packing;
  - prompt generation;
  - local LLM inference;
  - structured JSON answer;
  - logging.

#### Дополнительно реализовано
- добавлена **нормализация и валидация LLM-ответа** после генерации;
- если локальная модель возвращает неполный JSON или пропускает отдельные поля, ответ автоматически приводится к целевой структуре;
- гарантируется наличие следующих полей:
  - `summary`
  - `actions`
  - `kev`
  - `cwe`
  - `references`
  - `grounded`
  - `notes`
- в логах теперь сохраняются отдельно:
  - `raw_llm_answer`
  - `llm_answer` после нормализации
  - `final_answer`

#### Пример результата
На тестовом запросе по `CVE-2026-1731` локальный RAG-прототип:
- корректно извлёк релевантный контекст из корпуса;
- сформировал prompt на основе retrieval-контекста;
- передал его в локальную модель через Ollama;
- получил структурированный JSON-ответ;
- сохранил сырой и нормализованный результат в лог.

#### Итог
На текущем этапе реализован уже не mock, а **рабочий локальный RAG v0 прототип** с реальной локальной моделью.

Текущий контур работы:
`query -> retrieval -> context -> local LLM (Ollama) -> normalized structured answer -> logging`

#### Что это даёт
- прототип работает **без внешнего платного API**;
- архитектура остаётся расширяемой и допускает несколько backend-режимов:
  - `mock`
  - `ollama`
  - при необходимости позже может быть подключён и внешний API-провайдер;
- generation layer уже существует как отдельный модуль, а не как жёстко зашитая логика внутри retrieval.
